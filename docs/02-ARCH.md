## 1. 分层

```
┌──────────────────────────────┐
│ view/     界面与输入（DOM）    │  只读 store，只发 intent
├──────────────────────────────┤
│ store/    客户端状态（单一源）  │  由服务端帧驱动，不反向推导
├──────────────────────────────┤
│ net/      连接、握手、重连      │  只认协议，不懂业务语义
└──────────────────────────────┘
        ↑ 全部依赖 protocol/（帧类型定义）
```

**依赖规则（违反即 review 不通过）**

1. `view` 不得直接碰 WebSocket；只能 `intent.act(a, d)`。
2. `net` 不得读业务状态；它只负责"发帧、收帧、断线重连、关闭码处置"。
3. `store` 是唯一可变状态；视图层通过订阅渲染。
4. 帧类型只在 `protocol/` 定义，从服务端 `05` 抄字段名，不改名。

## 3. 运行模型

- **单线程事件循环**：WS 消息进来 → 更新 store → 标脏 → 下一帧（rAF）批量渲染。
- **不做本地预测**：移动、战斗、交易一律等服务端帧；界面只负责"已受理"与"倒计时"。
- **渲染节流**：`vital` 每秒一条，日志可能连发；渲染统一在 rAF 合批，避免每条消息都重排 DOM。

## 4. 关键取舍

| 取舍 | 选择 | 理由 |
|---|---|---|
| 框架 | 原生 DOM + 少量工具函数 | 面板多但结构简单；框架的 diff 成本高于手写局部更新 |
| 地图 | Canvas 画节点图，交互用命中测试 | 节点 ~90、边 ~170，DOM 画线太贵 |
| 日志 | 虚拟列表（固定行高 + 窗口化） | 挂机两小时会堆几千行，全量 DOM 会卡 |
| 状态 | 单一 store + 订阅 | 面板之间的同步靠同一个源，避免"背包更新了但角色页没变" |

## 5. 与服务端的一致性

- 协议版本：客户端内置 `PROTO = 1`，`hello` 回带；收到 4004 停止重连并提示升级。
- 动作名/错误码：从 `protocol/` 常量引用，不写字符串字面量，避免拼错。
- 帧字段：允许服务端新增字段（客户端忽略未知字段）；**字段改名视为破坏性变更**，要升 `proto`。
