## 1. 三类数据

| 类别 | 帧 | 频率 | 客户端怎么用 |
|---|---|---|---|
| 全量角色 | `state` | 变更即推 | **整体替换** `AppState::player`，不做字段级合并 |
| 高频小量 | `vital` | 每秒 | 只更新血/气/修为/体力/打坐态，不重建日志与表格 |
| 事件 | `log` | 随时 | 追加到环形缓冲；`lines[]` 逐行带 `k`（sys/nar/combat/good/bad） |
| 地图 | `map` | 请求后 | `look` / `worldMap` / `move` 后回包，覆盖当前节点视图 |

`state` 是全量快照，**不是增量**。背包、技能、装备、宗门、因果、功德、轮回都在里面；客户端不要自己拼"上一次 + 这次变化"。

## 2. 重绘策略（egui 的关键差异）

egui 只在需要时重绘，所以"什么时候请求重绘"就是这套架构的性能阀门：

| 触发 | 调用 | 说明 |
|---|---|---|
| 网络帧到达 | `ctx.request_repaint()` | 在 `NetEvent` 处理完、`store` 更新后统一调一次 |
| 有待显示的倒计时 | `ctx.request_repaint_after(500ms)` | 赶路、切磋回合、冷却；没有倒计时就不请求。切磋最后 5 秒与进度条插值改 100ms |
| 界面有动画（Toast 淡出、战报淡入） | `request_repaint_after(16ms)` | 动画结束立即停 |
| 纯待机 | 不请求 | 0 fps，CPU 占用接近 0 |

- 不要写"每帧都 `request_repaint()`"：那等于让 egui 变成 60fps 轮询，风扇会响。
- 不要用 `std::thread::sleep` 控制节奏；节奏由服务端帧与 `LocalDeadline` 决定。

## 3. 局部状态与缓存

| 内容 | 位置 | 失效条件 |
|---|---|---|
| 当前页 / 子标签 / 滚动位置 | `ui::UiState` | 切页时保留（回游戏页应在原滚动位置） |
| 输入框文本与频道 | `ui::UiState` | 发送成功后清空，历史另存 50 条 |
| 日志行排版（`Arc<Galley>`） | `ui::logview::LineCache` | 行数变化、字体变更、主题变更、宽度变化 |
| 表格排序 / 筛选 | `UiState` 各页字段 | 关闭页面不清；重连后保留 |
| 日志环形缓冲 | `store::logbuf`（5000 行） | 超出淘汰最早，`C-08` §2 |

排版缓存的做法：`LineCache` 用 `VecDeque<(u64 /*seq*/, Arc<Galley>)>`，只对**可见行**构建 LayoutJob；
缓存命中条件为 `(seq, width_bucket, theme_ver, font_ver)` 全等。这样滚动时不会每帧重排整屏。

## 4. 时钟与倒计时

- `offset = ready.server_now - now_ms()`；之后统一 `server_now() = now_ms() + offset`。
- 赶路：`travel.arrive_at` 是服务端毫秒时间戳，倒计时 = `arrive_at - server_now()`；到点后**不要自行切换界面**，等 `state` / `log` 的到达帧。
- 秘境每层限时、实时切磋每回合 15 秒：同样以服务端给的 `deadline` 为准。
- 系统休眠/唤醒后 `now_ms()` 会跳变，倒计时自然重算；不要把"经过的秒数"累加。
- 倒计时文本每秒最多变一次，不要在 `ui` 里格式化毫秒（除切磋最后 5 秒）。

## 5. 本地禁算清单

| 禁止 | 为什么 |
|---|---|
| 自行计算伤害、命中、掉落 | 服务端一次算完并给校验和；本地算会与战报不一致 |
| 自行判定赶路到达、切换节点 | 到达由 `state.loc` 决定，本地切了会"人还没到就能操作" |
| 自行累加修为/体力 | `vital` 每秒给权威值；本地累加会漂移 |
| 自行判定秘境通关/失败 | `dg` 的层数与 `over` 由服务端推 |
| 缓存并复用旧 `state` 做乐观更新 | 断线重连后旧值会覆盖新快照 |

## 6. 本地可以算的

- 冷却倒计时（基于最近一次动作回包时间 + 协议冷却表）。
- 日志的富文本高亮（按 `k` 上色、数字加粗）。
- 节点图布局（坐标由客户端算，服务端只给拓扑与地形）。
- 面板里的排序、筛选、搜索、分页。
- 数字的千分位与单位换算（显示层，不改数据）。

## 7. 多来源合并的顺序问题

同一秒里可能先来 `state`（血 40）再来 `vital`（血 38）。规则：

1. `vital` 只覆盖它自己带的字段，且**带上服务端时间戳**（若有）才覆盖更旧的值。
2. 没有时间戳时，以到达顺序为准：后到者胜。
3. `ready` 永远最优先：它是重连后的权威快照，到达即清空待合并队列。

## 8. Rust 落点

- `AppState` 持有 `player: PlayerView`、`world: WorldView`、`fight: FightView`、`social: SocialView`；各子结构各自带 `revision: u64`，`ui` 只比较它决定是否重排某块。
- 帧解析失败（`serde_json::Error`）不 panic：记 `tracing::warn!`、把原始帧写进 `logs/decode.log`，然后继续读下一帧。
  同一会话最多写 10 条，之后只累计计数并在设置页显示"本会话有 N 帧无法解析"。
- 所有时间戳用 `i64` 毫秒（与服务端一致）；只有展示"HH:MM:SS"时才用 `time` 格式化。
- `AppState` 不实现 `Clone`：避免有人图省事整份拷贝做对比；需要对比就用 `revision`。
