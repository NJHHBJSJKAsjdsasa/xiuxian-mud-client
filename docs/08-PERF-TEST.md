## 1. 帧预算

60fps 的预算是 16.7ms；本客户端**不追求满帧**，只在有动画/战斗时连续重绘，其余时间事件驱动。

| 状态 | 重绘频率 | 单帧 CPU | 说明 |
|---|---|---|---|
| 待机（无倒计时） | 0 fps | — | 不请求重绘；CPU 应 < 1% |
| 待机（有倒计时） | 2 fps | ≤ 2ms | `request_repaint_after(500ms)` |
| 日志滚动 / 悬停 | 跟随输入 | ≤ 4ms | 只排版可见行 |
| 战斗 / 切磋 | ≤ 60 fps | ≤ 6ms | 血条插值、倒计时环、战报淡入 |

| 工作 | 预算 | 超标时的做法 |
|---|---|---|
| 事件 drain + store 合并 | ≤ 0.5ms/帧 | 大批 `log` 合并成一次插入，逐条唤醒改为批量唤醒 |
| 布局计算 | ≤ 1ms | 减少嵌套 `Frame`/`ScrollArea`；表格只建可视行 |
| 日志排版 | ≤ 2ms | 可见行 galley 缓存（`C-04` §3）；宽度变化才失效 |
| 绘制提交 | ≤ 2ms | 少用 `Painter` 逐字绘制；图标走 `Shape` 复用 |
| 首帧 | ≤ 400ms | 字体 `include_bytes!` 免磁盘 IO；首帧只画骨架 |

**硬规则**：没有状态变化、没有动画、没有倒计时，就不请求重绘。
`request_repaint()` 只能出现在：网络帧到达、用户输入、动画进行中、倒计时进行中。

## 2. 上限

| 项 | 上限 | 超出 |
|---|---|---|
| 日志行 | 5 000 行 | 环形缓冲丢最早 |
| 单行日志 | 512 字符 | 截断并加省略号（双击看全文） |
| 聊天历史 | 200 条/频道 | 丢最早 |
| 表格 | 只建可视行 + 上下各 10 行 | 不 `for` 全量数据建控件 |
| 日志排版缓存 | 3 屏（约 120 行） | LRU 淘汰 |
| 解码失败样本 | 10 条/会话 | 之后只计数 |

## 3. 内存

- RSS 目标：空闲 < 120MB，挂机 2 小时增长 < 15%。
  （egui + wgpu + 字体子集 + GPU 驱动基线约 60–90MB，比 TUI 高是必然的，不要拿 TUI 的数字当目标。）
- GPU 显存目标 < 150MB：不给日志行建纹理缓存到无上限；`LineCache` 只留 3 屏。
- 不缓存整份 `state` 历史；只保留当前快照与必要派生（背包索引、技能名映射）。
- 日志行用 `String`，不做跨行切片；避免为省内存引入生命周期复杂度。
- 已读取的图片/曲线数据：曲线最多保留 90 天点，超出按周聚合。

## 4. 测试矩阵

| 类别 | 用例 | 判定 |
|---|---|---|
| 握手 | 正常 `proto`；不带 `proto`；超版本 | 超版本必须提示升级且不重连 |
| 重连 | 断网、系统休眠 30 分钟唤醒、服务端重启 | 3 秒内恢复；`ready` 后界面与服务端一致 |
| 顶号 | 同账号第二个连接 | 旧连接提示"账号在别处登录"，不重连 |
| 战斗 | 单怪 / 三怪 / 组队遇战 / 团灭 | 帧序不丢、目标选择生效、`over` 后控件禁用 |
| 实时切磋 | 双方出手推进、超时、认输、对手掉线 | 倒计时准确；结算有原因 |
| 秘境 | 进本、切层、掉线 5 分钟内重连 | 回同层同进度；超 5 分钟回不去 |
| 经济 | 挂单、撤单、成交、拍卖出价/被超 | 数值与服务端一致，不本地加减 |
| 长挂机 | 2 小时打坐 + 间歇战斗 | 内存平稳、日志截断正常、帧率不退化 |
| 窗口 | 1024×640 / 1280×800 / 1920×1080 / 2560×1440 | 不错位、不截断关键按钮 |
| 缩放 | 100% / 125% / 150% / 200% | 文字清晰、点击命中准确 |
| 字体 | 生僻字、繁体、emoji、缺字 | 无豆腐块；缺字有 warn 记录 |

## 5. 自动化怎么跑

```bash
cargo test                     # 单元：协议解析、store 合并、时间偏移、文本处理
cargo test --test ui           # egui_kittest 交互与快照
cargo test --test replay       # 帧回放（JSONL）
cargo clippy --all-targets -- -D warnings
cargo fmt --check
python tools/doc-check.py
```

- **协议解析**：把 `05` 里的样例帧写成 `tests/fixtures/*.json`，逐个反序列化并断言关键字段。
- **store 合并**：`state` / `vital` / `ready` 三种到达顺序，断言最终值一致。
- **时间**：固定 `ready.server_now` 与本地时钟，断言倒计时计算（不依赖真实时间）。
- **文本**：千分位、80 字截断（按字符不按字节）、长行省略。

UI 测试用 `egui_kittest`（官方，0.37 起支持快照与视频录制）：

```rust
let mut harness = Harness::new_ui(|ui| ui::views::game::draw(ui, &state, &mut ui_state));
harness.run();
harness.get_by_label("断崖").click();
harness.run();
assert!(ui_state.pending_move.is_some());
```

- 快照测试只覆盖 3 个稳定画面：主界面空日志、战斗三怪、交易行表格；其余用控件断言，避免像素抖动导致假红。
- 不做端到端自动化（不驱动真实窗口）；真实窗口只在手测矩阵里验。

## 6. 帧回放

- 录制：`--record frames.jsonl` 把收发的每一帧按 `{dir, ts, frame}` 写入文件。
- 回放：`cargo run -- --replay frames.jsonl` 驱动 store 与渲染，不连服务端。
- 截图：`--replay ... --snapshot out.png --at-frame 120` 在离屏 `egui::Context` 里跑 N 帧后存 PNG，
  用于 PR 里贴"改前/改后"。
- 断言：最终状态与录制结束时一致；关键帧（`over`、`winner`、`duels`）都被消费一次。
- 回放文件不入库，只放 `tests/fixtures/` 的小样本（< 200KB）。

## 7. 复用服务端脚本做联调

服务端仓库 `tools/` 下的脚本可以直接当"对照答案"：

| 脚本 | 能验证客户端的什么 |
|---|---|
| `tools/smoke.mjs` | 登录/建号/打坐/历练的主链路顺序与字段 |
| `tools/travel-check.mjs` | `move` 的受理与到达时刻、地形门槛文案 |
| `tools/party-fight-check.mjs` | `battle` 多怪、目标选择、`pvpResult`、`live` 实时切磋的帧序 |
| `tools/gw-check.mjs` | 宗门战从下书到战果的完整帧 |
| `tools/market-check.mjs` | 交易行挂单/成交/历史的字段 |

做法：先跑脚本看服务端真实输出，再对照客户端渲染；两边不一致时以服务端为准。
