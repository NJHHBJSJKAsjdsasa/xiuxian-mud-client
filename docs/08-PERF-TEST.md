## 1. 轮询预算

主循环固定 30ms 一轮（约 33 次/秒），每轮：drain 网络 → 处理按键 → 全量画一屏。

| 工作 | 预算 | 超标时 |
|---|---|---|
| drain + store 合并 | ≤ 0.5ms | 大批 `log` 合并插入；一次最多消费 512 条 |
| 布局计算（七段 + 数据页） | ≤ 1ms | 数据页只渲染可视行；表格不做全量拼接 |
| 字符场景生成（120×20 网格） | ≤ 1ms | 只在尺寸/地形/天气变化时重建，其余复用缓存 |
| 写屏（ratatui diff） | ≤ 3ms | 减少无效 Span；同色合并成一段 |
| 整轮 | ≤ 8ms | 仍有 22ms 余量 |

**硬规则**：轮询间隔 30ms，不因"没变化"而跳过绘制。
终端只更新变化的单元格（ratatui 自己做 diff），跳帧没有收益，反而会让按键响应变慢。

## 2. 上限

| 项 | 上限 | 超出 |
|---|---|---|
| 日志行 | 5 000 行 | 环形缓冲丢最早 |
| 单行日志 | 512 字符 | 截断并加省略号（`Enter` 看全文） |
| 聊天历史 | 200 条/频道 | 丢最早 |
| 数据页行数 | 取终端高度 | 超出部分靠 PgUp/PgDn（M5） |
| 可见日志 | 7 行（见闻段高度） | 只取末尾 7 条 |
| 解码失败样本 | 10 条/会话 | 之后只计数 |

## 3. 内存

- RSS 目标：空闲 < 25MB，挂机 8 小时增长 < 10%（实测 debug 约 12MB，release 更低）。
- CPU：空闲 < 1%（一个核的百分比）；打坐时同样是 30ms 轮询，不额外加速。
- 无显存占用：只有字符网格，不上传纹理、不做曲线。
- 不缓存整份 `state` 历史；只保留当前快照与必要派生（背包索引、技能名映射）。
- 日志行用 `String`，不做跨行切片；环形缓冲封顶 5000 行。

## 4. 测试矩阵

| 类别 | 用例 | 判定 |
|---|---|---|
| 握手 | 正常 `proto`；不带 `proto`；超版本 | 超版本必须提示升级且不重连 |
| 重连 | 断网、系统休眠 30 分钟唤醒、服务端重启 | 3 秒内恢复；`ready` 后界面与服务端一致 |
| 顶号 | 同账号第二个连接 | 旧连接提示"账号在别处登录"，不重连 |
| 战斗 | 单怪 / 三怪 / 组队遇战 / 团灭 | 帧序不丢、目标选择生效、`over` 后控件禁用 |
| 终端尺寸 | 80×24 / 120×40 / 200×60 | 不截断关键信息；场景高度自适应 |
| 字符宽度 | 全中文 / 中英混排 / 生僻字 | 列对齐；无重叠；缺字显示为 `?` 而不是乱码 |
| 颜色 | 真彩 / 256 色 / 无色 | 真彩正常；256 色可读；无色仍能靠字形区分 |

## 5. 自动化怎么跑

```bash
cargo test                     # 单元：协议解析、store 合并、时间偏移、文本处理
cargo test --test ui           # TestBackend 交互与快照
cargo test --test replay       # 帧回放（JSONL）
cargo clippy --all-targets -- -D warnings
cargo fmt --check
python tools/doc-check.py
```

- **协议解析**：把 `05` 里的样例帧写成 `tests/fixtures/*.json`，逐个反序列化并断言关键字段。
- **store 合并**：`state` / `vital` / `ready` 三种到达顺序，断言最终值一致。
- **时间**：固定 `ready.server_now` 与本地时钟，断言倒计时计算（不依赖真实时间）。
- **文本**：千分位、80 字截断（按字符不按字节）、长行省略。

UI 测试用 ratatui 的 `TestBackend`：把一帧画进内存 buffer，断言单元格内容。

```rust
let mut term = Terminal::new(TestBackend::new(120, 40))?;
term.draw(|f| render::draw(f, &app))?;
let text: String = term.backend().buffer().content.iter().map(|c| c.symbol()).collect();
assert!(text.contains("历练"));
assert!(text.contains("青云·樵径"));
```

- 快照测试只覆盖 3 个稳定画面：主界面、数据页、舆图；断言关键字而不是逐字符比对，避免主题微调导致假红。
- 不做端到端自动化（不驱动真实终端）；真实终端只在手测矩阵里验。

## 6. 帧回放

- 录制：`--record frames.jsonl` 把收发的每一帧按 `{dir, ts, frame}` 写入文件。
- 回放：`cargo run -- --replay frames.jsonl` 驱动 store 与渲染，不连服务端。
- 截图：`--snapshot out.ansi` 在 `TestBackend` 里跑 6 秒后把整屏导出为 ANSI 文本，
  再转成 PNG（脚本见 `tools/ansi2png.py`）用于 PR 贴"改前/改后"。
- 断言：最终状态与录制结束时一致；关键帧（`over`、`winner`、`duels`）都被消费一次。
- 回放文件不入库，只放 `tests/fixtures/` 的小样本（< 200KB）。

## 7. 复用服务端脚本做联调

服务端仓库 `tools/` 下的脚本可以直接当"对照答案"：

| 脚本 | 能验证客户端的什么 |
|---|---|
| `tools/smoke.mjs` | 登录/建号/打坐/历练的主链路顺序与字段 |
| `tools/travel-check.mjs` | `move` 的受理与到达时刻、地形门槛文案 |
| `tools/party-fight-check.mjs` | `battle` 多怪、目标选择、`pvpResult`、`live` 实时切磋的帧序 |
| `tools/gw-check.mjs` | 宗门战从下书到战果的完整帧 |
| `tools/market-check.mjs` | 交易行挂单/成交/历史的字段 |

做法：先跑脚本看服务端真实输出，再对照客户端渲染；两边不一致时以服务端为准。
